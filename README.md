### 線上專案進度時間軸表 — 系統總結與注意事項

**一、整體架構**

-   **專案清單頁**：所有「線上專案」（例如：呼吸照護病房病房助理工作流程、庫存管理…）的入口，可新增／修改／刪除／搜尋專案，點進去才進入該專案的時間軸編輯頁。
-   **時間軸編輯頁**：每個專案內有多個「班別」（例如 D白班、A收料…），每個班別下有多筆「項目」（代號、名稱、起訖時間、時間內說明、輔助連結），畫在一條 07:00～翌日06:59 的時間軸上。
-   所有資料存在 Firebase Firestore，**多裝置即時同步**——別人在別台裝置改了，畫面會自動更新（但編輯視窗開著時不會被打斷，等您關閉視窗才套用外部更新，避免正在打字被蓋掉）。

**二、目前完整功能**

| 層級 | 新增 | 修改 | 刪除 | 查詢 |
| --- | --- | --- | --- | --- |
| 專案 | ✓ | ✓ | ✓（名稱不可重複） | 清單頁搜尋框 |
| 班別 | ✓ | ✓（✎ 按鈕） | ✓（內有項目時禁止刪除，需先清空項目） | 同專案內名稱不可重複 |
| 項目 | ✓（＋按鈕/表格新增） | ✓ | ✓ | 代號同班別內不可重複 |

其他：**資料表檢視/編輯**（表格模式，可整批修改儲存）、**匯出備份(XML)**、**匯入XML**（可合併既有資料）、編輯中離開會自動存草稿到本機（意外關閉分頁可還原）。

**三、使用注意事項**

1.  **請務必下載檔案在本機（或直接開啟已部署的網址）開啟使用，不要一直透過對話框的檔案預覽視窗看**——每次我更新檔案重新送出時，預覽視窗會自動重新整理，看起來像「畫面被刷新、編輯不見」，其實不是程式問題。
2.  **刪除班別前要先刪空裡面的項目**：這是您要求的新規則，避免不小心整批誤刪掉還在用的項目資料。
3.  「代號」限兩位數字，同一班別內不可重複；同一專案內班別名稱不可重複；專案名稱本身也不可重複。
4.  時間軸資料的實際存放位置：舊的（原本就有真實資料的）專案存在 Firestore 頂層 `shifts` 集合；**新建立的專案**則各自存在 `projects/{專案ID}/shifts` 子集合，彼此獨立不會互相污染。
5.  目前的「鍵值」（如專案名稱、專案+班別、專案+班別+代號+項目名稱）是靠 Firestore 自動產生的文件 ID 對應，不是直接用中文字串當鍵——這部分之前提過，如果您希望改成正式的「資料結構規格書」文件，或想把鍵值實際改成組合字串儲存，都可以再跟我說，目前先維持現狀。

# 一、文件目的

本文件記錄「線上專案進度時間軸表」系統的邏輯資料結構（主檔／明細檔／鍵值），對應目前實際採用 Firebase Firestore 的實體儲存方式，讓後續維護或串接其他系統時，能清楚掌握每一層資料的欄位與鍵值組成。

# 二、資料層級總覽

系統共分為四張邏輯表，由上而下形成「專案 → 班別 → 項目」三層架構：

| 層級 | 說明 | 邏輯表名稱 |
| --- | --- | --- |
| 第 1 層 | 線上專案（例如：呼吸照護病房病房助理工作流程、庫存管理） | 線上專案主檔 |
| 第 2 層 | 專案底下的班別（例如：D白班、A收料） | 線上專案明細檔 |
| 第 2 層（同鍵） | 班別在時間軸表頁面的呈現設定 | 線上專案進度時間軸表主檔 |
| 第 3 層 | 班別底下的項目（例如：代號 04、驗收作業，07:50–11:00） | 線上專案進度時間軸表明細檔 |

# 三、各表欄位與鍵值定義

## 3.1　線上專案主檔

每一筆代表一個可獨立編輯的線上專案。

| 欄位名稱 | 型別／格式 | 說明 |
| --- | --- | --- |
| 線上專案名稱 | 文字（唯一） | 專案顯示名稱，新增／修改時系統會檢查同名專案是否已存在 |
| 線上專案名稱功能說明 | 文字（多行） | 顯示在專案清單頁卡片上的簡介 |
| 排序 order | 數字 | 控制專案清單的顯示順序 |
| legacy 標記 | 布林值 | 標記是否為系統最初就存在的專案；為真者資料存放位置與新建專案不同（詳見第四節），且不可被刪除 |

**鍵值：**線上專案名稱

## 3.2　線上專案明細檔（班別基本資料）

每一筆代表某專案底下的一個班別。

| 欄位名稱 | 型別／格式 | 說明 |
| --- | --- | --- |
| 線上專案名稱 | 文字 | 所屬專案（對應 3.1 的鍵值） |
| 各班名稱 | 文字（同專案內唯一） | 班別顯示名稱，新增／修改時系統會檢查同專案內是否已有同名班別 |
| 功能說明 | 文字（多行） | 班別的工作流程說明，顯示在班別名稱下方 |

**鍵值：**線上專案名稱＋各班名稱

## 3.3　線上專案進度時間軸表主檔（班別時間軸設定）

與 3.2 為同一個班別，多出時間軸呈現所需的欄位；系統實作上與 3.2 合併為同一筆資料，不另外分開儲存。

| 欄位名稱 | 型別／格式 | 說明 |
| --- | --- | --- |
| 線上專案名稱 | 文字 | 所屬專案 |
| 各班名稱 | 文字 | 所屬班別 |
| 色系 colorKey | 文字 | 決定該班別在時間軸上色塊的顏色 |
| 排序 order | 數字 | 控制班別在時間軸上的排列順序（由上而下） |

**鍵值：**線上專案名稱＋各班名稱

## 3.4　線上專案進度時間軸表明細檔（項目）

每一筆代表某班別底下的一個時間軸項目，是整個系統資料量最大、變動最頻繁的一層。

| 欄位名稱 | 型別／格式 | 說明 |
| --- | --- | --- |
| 線上專案名稱 | 文字 | 所屬專案 |
| 各班名稱 | 文字 | 所屬班別 |
| 代號 | 兩位數字（同班別內唯一） | 例如 01、02…04；新增／修改時系統會檢查同班別內代號是否重複 |
| 項目名稱 | 文字 | 工作項目名稱 |
| 開始日期時間 | 日期＋時間 | 系統內部換算為「當日 00:00～翌日 23:59」的絕對分鐘數（0～2880），畫面顯示以 07:00 為時間軸起點 |
| 結束日期時間 | 日期＋時間 | 同上，絕對分鐘數，需大於開始時間 |
| 時間內說明 | 文字（多行） | 該時段內的工作內容說明 |
| 輔助說明連結 | URL | 選填，額外的參考連結 |

**鍵值：**線上專案名稱＋各班名稱＋代號（兩位數字）＋項目名稱

# 四、目前系統的實體儲存方式（重要）

上述四張表的「鍵值」是邏輯設計，方便理解資料之間的從屬關係與唯一性規則。但系統目前在 Firebase Firestore 中，實際上並不是用「線上專案名稱＋各班名稱＋代號＋項目名稱」這種組合字串本身當作資料庫的實體鍵，而是採用以下方式：

| 邏輯表 | Firestore 實體位置 | 實體鍵 |
| --- | --- | --- |
| 線上專案主檔 | 頂層 projects 集合 | Firestore 自動產生的文件 ID |
| 線上專案明細檔／時間軸表主檔（班別） | legacy 專案：頂層 shifts 集合新建專案：projects/{專案文件ID}/shifts 子集合 | Firestore 自動產生的文件 ID |
| 時間軸表明細檔（項目） | 存放於所屬班別文件內的 tasks 陣列欄位中 | 陣列元素各自帶有系統產生的項目 ID（非資料庫文件） |

_換句話說：邏輯上的「唯一性」（同名不可重複、代號不可重複）是由應用程式邏輯在新增／修改時主動檢查並擋下，而不是由資料庫的複合鍵直接保證。這是目前系統採用的作法，優點是彈性高、修改名稱不需要搬動整批資料；如果您希望改成資料庫實際用組合字串當鍵值（例如文件_ _ID_ _直接命名為「呼吸照護病房病房助理工作流程__\_D__白班」），可以再另外安排一次資料結構調整，屬於較大幅度的改動，建議先確認是否有實際需要（例如要串接其他外部系統、需要用鍵值直接查詢）再進行。_

# 五、目前已落實的資料完整性規則

| 規則 | 說明 |
| --- | --- |
| 專案名稱不可重複 | 新增／修改專案時檢查 |
| 同專案內班別名稱不可重複 | 新增／修改班別時檢查 |
| 同班別內項目代號不可重複 | 新增／修改項目時檢查（表單與表格編輯模式皆檢查） |
| 班別內有項目時禁止刪除該班別 | 需先清空班別內所有項目，才能刪除班別本身，避免誤刪整批項目資料 |
| legacy 專案不可刪除 | 保護系統最初就存在的真實資料 |
